# OrnaVision (Gold Ornaments Similarity Search) Project Report

This report outlines the architecture, technology stack, and complete workflow from local development to production deployment for the **OrnaVision (GSS)** project.

---

## 1. Technology Stack

### Frontend (Client-Side)
The frontend is built for simplicity, performance, and cross-browser compatibility without relying on heavy frameworks.
* **Core:** Vanilla HTML5, CSS3, and JavaScript (ES6+).
* **Styling:** Custom CSS (`style.css`, `compare.css`, `admin.css`) providing responsive, mobile-friendly layouts, glassmorphism aesthetics, and smooth animations.
* **API Communication:** Native JavaScript `Fetch API` for handling asynchronous requests (image uploads, text search, and comparisons) to the backend.

### Backend (Server-Side)
The backend is a robust Python-based service designed to serve REST APIs and handle complex Machine Learning (ML) inference.
* **Framework:** Flask (Python web framework) with Werkzeug.
* **Server/WSGI:** Gunicorn configured with `gthread` workers to manage multi-threaded, memory-efficient request handling.
* **Environment Management:** `python-dotenv` for managing sensitive keys (API Keys, Azure connection strings, Qdrant URLs).

### Machine Learning & Artificial Intelligence
The project relies on state-of-the-art vision and language models to understand and search for jewelry.
* **PyTorch & Torchvision:** Core deep learning framework used for all local model inference.
* **ConvNeXt Base:** A fine-tuned visual model used for:
  1. Classifying jewelry into one of 13 specific categories (e.g., Bangles, Necklaces, Rings).
  2. Acting as a feature extractor to generate visual embeddings for exact pattern matching and comparison.
* **CLIP (Contrastive Language-Image Pretraining):** Used to map both text (user queries) and images into the same embedding space, enabling:
  * Text/Voice-to-image search.
  * Detecting visual attributes (stones, shapes).
  * Extracting comprehensive design features.
* **LLM Integration (Groq API / Qwen 3.8-27b):** Provides natural language understanding to extract visual keywords from conversational user queries and generates rich metadata for newly uploaded or uncataloged images using vision-language capabilities.

### Data Storage & Cloud Infrastructure
* **Vector Database (Qdrant Cloud):** Stores the high-dimensional embeddings generated by ConvNeXt and CLIP. It performs lightning-fast cosine similarity searches to find visually matching jewelry.
* **Blob Storage (Azure Blob Storage):** Safely stores the actual high-resolution image files (both the cataloged dataset and user uploads).
* **Hosting/Deployment (Azure App Service):** A fully managed Platform as a Service (PaaS) that runs the Dockerized/Linux containerized backend and scales according to traffic.

## 2. System Workflow & Process

### A. Image Search Workflow
1. **Upload:** The user uploads an image of an ornament via the frontend UI.
2. **Transfer:** The JS Fetch API sends the image as `multipart/form-data` to the Flask backend (`/api/search`).
3. **Classification:** The backend loads the image and runs it through the fine-tuned **ConvNeXt** model to predict the jewelry category (e.g., "Necklace").
4. **Feature Extraction:** 
   * The image is passed through the **ConvNeXt feature extractor** to get visual vectors (texture, layout, craftsmanship).
   * The image is also passed through the **CLIP model** to extract semantic attributes (stone type, shape).
5. **Vector Search:** The backend queries **Qdrant Cloud** with these embeddings, filtering by the predicted category.
6. **Result Generation:** Qdrant returns the closest matching items. The backend formats these with metadata (prices, weights) and returns JSON.
7. **Rendering:** The frontend dynamically renders the matching ornaments in a grid.

### B. Text & Voice Search Workflow
1. **Input:** The user types a query or uses speech-to-text (e.g., "heavy traditional gold bridal necklace").
2. **Intent Parsing:** The query is sent to the **Groq LLM**, which acts as a jewelry assistant, filtering out non-jewelry queries and extracting only the relevant visual keywords.
3. **Vectorization:** The backend converts these keywords into embeddings using the **CLIP text encoder**.
4. **Search & Return:** The text embeddings are used to query **Qdrant**, matching against the image embeddings in the database. Results are returned to the user.

### C. Image Comparison Workflow
1. **Trigger:** The user selects an uploaded image and a search result to compare them side-by-side.
2. **Parallel Inference:** The backend batches both images into a single tensor and processes them simultaneously through **ConvNeXt** and **CLIP** to save time and GPU/CPU cycles.
3. **Comprehensive Analysis:** The backend compares:
   * **Metadata:** Prices, categories, and tags.
   * **Attributes:** Analyzes if the stones and shapes match.
   * **Visual Similarity:** Calculates the exact cosine similarity score between the two ConvNeXt feature vectors.
4. **Summary:** An AI-generated list of differences and similarities is sent back to the frontend to populate the comparison modal.

## 3. Production Deployment Process

Deploying the application from a local environment to Azure App Service involves the following lifecycle:

1. **Local Development & Optimization:**
   * Code is written and tested locally. 
   * Memory usage is heavily profiled. *(For example, combining the classification and feature extraction ConvNeXt models into a single shared memory instance to prevent Out-Of-Memory (OOM) crashes on the server).*
   * Environment variables (`.env`) are used to point to local or dev services.

2. **Version Control:**
   * All changes are committed and pushed to a remote repository (e.g., GitHub).

3. **Environment Configuration on Azure:**
   * The Azure App Service environment is configured via the Azure Portal.
   * Production secrets (Qdrant API keys, Groq API keys, Azure Storage Connection Strings) are injected securely into the App Service's **Environment Variables** / Application Settings.
   * `WEB_TIMEOUT` and worker limits are set to accommodate the AI inference times.

4. **Continuous Integration / Continuous Deployment (CI/CD):**
   * Azure App Service is hooked up to the GitHub repository.
   * When new code is pushed to the `main` branch, Azure automatically triggers a build process using GitHub Actions or Kudu (Azure's deployment engine).
   * The build process installs all dependencies listed in `requirements.txt` (PyTorch, Flask, timm, etc.).

5. **Server Initialization (Gunicorn):**
   * Once deployed, Azure starts the application using the startup command defined for the service (typically running Gunicorn: `gunicorn -c gunicorn_conf.py app:app`).
   * Gunicorn manages the worker threads. As the first request hits the server, the PyTorch models are lazily loaded into the server's RAM in a thread-safe manner (using `threading.RLock`).

6. **Live Production:**
   * The frontend assets (HTML/JS/CSS) are served to the user's browser.
   * API calls are securely routed through Azure's load balancers to the Python backend, handling thousands of similarity queries backed by Qdrant and Azure Storage.
